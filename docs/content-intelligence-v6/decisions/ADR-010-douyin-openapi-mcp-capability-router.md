# ADR-010：抖音 OpenAPI 采用 Manifest 驱动的 MCP 能力路由

- 状态：采用
- 日期：2026-08-16
- 证据：`LEDGER.md` A25-A27

## 背景

抖音开放平台当前移动/网站应用目录包含 13 张能力表与 119 个目录条目，覆盖账号授权、粉丝关系与画像、内容、搜索、私信群聊、生活服务、素材、服务市场、小程序推广计划、分身技能数据和汽水音乐。目录条目不等于可主动调用的 OpenAPI：其中混有 OAuth、平台回调给商家的接口和要求接入方实现的接口。逐条把它们注册成 Lead 工具会造成工具选择噪声、权限混淆和上下文膨胀，也会复制令牌、分页、错误处理、幂等与审批逻辑。

官方提供统一服务端 SDK，支持 Java、NodeJS 和 Go，并要求调用方自行注入 Token。官方还明确提示单实例凭据实现用于多实例部署时可能发生 Token 互刷。第六版后端是 Python，因此 SDK 不能直接成为领域层依赖；MCP 正适合作为独立协议边界。

Apache Doris MCP Server 1.0.0 已于 2026-08-01 发布并把同类问题做成正式公共合同：把大量平铺工具收敛为 8 个稳定领域入口和 55 个渐进披露子能力。领域空对象调用返回当前身份与路由下的精确 Schema、可用性和确定性 `manifest_version`；执行时重新鉴权、重新探测、校验 Manifest、输入和输出。发布后的修复 `#199` 又增加“单领域优先”：Host 先选择唯一最匹配领域，不为显得完整而推测性打开多个 Manifest；领域说明同时写明职责和排除项。该实现通过 Apache-2.0 发布，但其运行时、探测对象和只读约束均针对 Doris，故本项目采用协议模式而不直接引入其数据库运行时代码。

## 决策

1. 建立独立的 `douyin-openapi-mcp`。当前作为 DeerFlow 持久 stdio 会话中的独立进程运行；未来账号级凭据代理需要跨进程持久化时，可保持同一合同改为仅监听本机的 HTTP MCP。DeerFlow 只通过 MCP 使用全量抖音能力，内容智能内核仅保留现有搜索兼容入口，不保存其他平台 URL、Scope 或令牌规则。
2. 将全部官方目录条目编入版本化 Catalog，而不是全部暴露为模型工具。每项至少记录 `operation_id`、领域、官方文档、交互方向 `outbound / inbound_webhook / provider_implemented / auth`、SDK 方法、HTTP 方法、URL、Scope、鉴权模式、读写等级、幂等要求、输入 Schema、输出投影和审阅状态。只有已审阅的主动调用项才能成为 Child。
3. MCP 首层只暴露一组短小、稳定、职责互斥的领域工具。领域数量由目录边界、每域 Child 数量和 Manifest 字节预算决定，不机械照搬 Doris 的 8 个；调用任一领域的 `{}` 才返回该领域的授权子能力。未经授权的子能力不披露，已授权但未开通、缺少账号授权或暂时故障的子能力仍以 `callable=false` 和稳定原因码出现，便于 Agent 诚实解释而不猜测。
4. Manifest 由官方目录、接口页和 SDK 表生成后人工审阅、锁版本和哈希。运行时不抓官方文档生成调用，也不允许模型提供任意 URL、HTTP 方法或 Scope。
5. 鉴权代理区分三类凭据：应用级 `stable_client_token`、账号级 `access_token/open_id`、特定业务域凭据。凭据只在 MCP 内部使用；Cookie、Client Secret、Token 和刷新令牌不得进入模型、前端、工具回执、日志或测试。
6. 应用级稳定令牌按应用缓存，并在失效错误后最多刷新重试一次。账号级令牌绑定用户、应用和平台账号，不能跨用户或跨账号复用。
7. 调用按风险分级：公开只读可自动执行；授权账号只读需先验证账号所有权；创建、修改、发送、删除、扣减、发布和交易类操作必须经过内容绑定审批、幂等键和结果对账。
8. 所有结果统一为 `data / warnings / metadata` 回执，并在越过 MCP 边界前执行输出 Schema 校验。元数据保存操作 ID、Manifest 版本、账号引用、请求哈希、平台日志 ID、分页游标和证据角色；大响应留在本地工件中，只给 Lead 有界投影。
9. 普通搜索结果固定为 `topic_evidence`。一条视频或账号页不能升级成对标账号分析。授权账号的粉丝数据只用于该账号复盘；任意竞品的受众与账号拆解仍需独立身份、多作品和覆盖回执。
10. 先用“抖音视频搜索”完成端到端纵向验收，再扩展同鉴权、同风险的只读接口。Manifest 收录不等于生产可用；每项必须通过权限、真实响应和边界测试后才能标为 enabled。
11. 领域与子能力选择使用精确 ID，不增加概率式意图分类器。Agent 选择领域，Manifest 提供完整授权子集，调度器只执行一个精确 Child；不得模糊匹配 API 名称或让模型自行拼 URL、Scope 与 HTTP 方法。
12. Manifest 版本由领域合同、子能力合同、应用/账号授权代际、平台能力代际和审批策略代际共同生成。执行前重新生成；不一致返回 `stale_manifest` 并要求重新发现，禁止拿旧权限和旧 Schema 继续调用。
13. 对上下文设硬预算：顶层工具列表、单领域 Manifest、单项描述、输入 Schema、输出 Schema、枚举和最终回执均必须有字节或数量上限，超限在启动或构建阶段失败，不能等到模型上下文爆掉才处理。
14. 能力目录是唯一源代码真相，机器可读目录、MCP Schema、文档清单和迁移表由同一份定义生成并在 CI 检查漂移，不手工维护四份事实。
15. Host 每次先选一个最匹配领域，只发现该领域的 Manifest；不能为回答看起来完整而并行展开多个领域。顶层领域描述必须同时声明“负责什么”和“明确不负责什么”。用户后续问题改变时可以立即切换领域，这不是固定工作流硬门。

## MCP 表面

全目录预算审计后冻结为 16 个互斥领域：`douyin_identity`、`douyin_audience`、
`douyin_content`、`douyin_search`、`douyin_messaging`、`douyin_interest_events`、
`douyin_local_shops`、`douyin_local_fulfilment`、`douyin_local_goods`、
`douyin_local_audience`、`douyin_local_affiliate`、`douyin_assets`、
`douyin_service_market`、`douyin_creator_partnerships`、`douyin_clone_leads` 和
`douyin_music`。最大领域为 18 条目录记录，低于 32 条预算。每个顶层描述同时写明
`includes` 与 `excludes`；本轮采用的 Child 只有 `video_search` 和
`experience_search`，其余目录项不出现在模型 Manifest 中。

全局能力状态由控制面和各领域的空对象发现提供，不再单独暴露一个与所有领域重叠的 `douyin_capabilities` 给模型。生活服务目录过大，完成预算审计后很可能拆成门店、券订单、商品和推广等互斥领域；不能为了凑 8 个把几十个 Child 塞回一个巨型 Manifest。

每个领域工具以 `{}` 发现当前授权 Manifest，再接收其中的 `child_tool`、`arguments` 和 `manifest_version`。调度器必须二次校验身份、应用、账号、Scope、可用性、Schema 和风险，不能相信模型声称某能力已经开通。Host 若确实不支持渐进披露，可以从同一目录生成扁平兼容表面，但第六版 DeerFlow 默认只使用分层模式。

Doris 1.0 的内置合同全部只读，因此它只为本项目提供“发现与精确执行”的成熟参考。抖音的发布、私信、删除、交易等写操作仍必须额外实现内容绑定审批、幂等键、费用上限、未知结果对账和禁止盲重试；这些边界不能因为借用了 Doris 架构而省略。

## 不采用

- 不把 119 个目录条目和规则塞进 Lead 提示词。
- 不为每个 API 手写一份互不共享鉴权和错误处理的工具。
- 不提供可调用任意 URL 的通用 HTTP 工具。
- 不因官方目录存在某接口，就假定当前应用、当前账号或当前主体已经获批。
- 不用 OpenAPI 的自有账号数据冒充竞品数据。

## 验收

- Manifest 能检测官方 URL、Scope 或 Schema 漂移，并在未审阅时拒绝调用。
- 两个并发调用只获取一次有效稳定令牌；过期时只刷新并重试一次。
- 两用户、同平台多账号的账号级 Token 和回执完全隔离。
- 搜索、粉丝画像、素材上传和删除分别覆盖公开读、授权读、可恢复写和不可逆写四种风险等级。
- 顶层工具列表保持稳定；领域 Manifest 隐藏未授权 Child，并让已授权但不可用的 Child 返回明确原因码，不让模型自行补造参数。
- 顶层领域数量通过互斥性与上下文预算验收；领域发现隐藏未授权 Child，但保留已授权而不可调用 Child 的状态和稳定原因码。
- 一次普通任务只展开一个领域 Manifest；多领域需求必须有用户问题中的明确依据，不能为了完整感推测性展开。
- 修改 Scope、账号授权、应用资质、Manifest Schema 或审批策略后，旧 `manifest_version` 必须确定性失效。
- 目录生成的 MCP Schema 与文档清单在 CI 中保持一致，任何一方手工漂移都会失败。
- 真实响应中任何密钥、Token、Cookie、临时素材 URL 和未投影敏感字段均不进入 Lead 上下文。
