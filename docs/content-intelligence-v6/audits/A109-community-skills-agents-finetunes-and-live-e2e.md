# A109 Skills、改造型 Agent、微调模型与真实端到端审计

## 研究问题

A108 已经审计论文、厂商指南和经验记忆方法。本轮继续回答两个更实际的问题：社区是否已有可直接采用的
营销 Skills、改造型 Agent 或微调模型；第六版从“我是做什么的”到账号路线、用户确认和具体选题的真实
端到端链路，现在究竟能不能工作。

## 结论

社区已经提供了大量优秀的**局部能力**，但没有一个开箱即用的模型、Skill 包或第二 Agent 运行时能替代
第六版要解决的“商业表达 -> 长期内容世界 -> 具体可拍选题”。最适合当前系统的组合仍是：

> **一个 DeerFlow Lead 负责最终收敛，认知步骤使用有界结构化工作者，方法 Skills 按任务加载，平台与
> 搜索工具提供证据，用户确认和真实结果进入追加式台账。**

本轮真实运行也证明，现役链路已经能产出合格内容方向，但仍有运行成本和事实边界问题。旧书案例最终得到
“书页上的印迹：藏书印如何让一部古书记住每一任主人”。用户复核认为该题通过：它不是继续讲旧书买卖，
而是把藏书印当作物证，进入历任主人和时代故事，与“抗战家书总编”一类从物证进入人的编辑方法相通。

## 微调模型审计

| 模型 | 已观察用途 | 当前判定 |
| --- | --- | --- |
| `suehuynh/Marketing-Llama-3.3-70B` | 英文 LoRA，约 1.3 万条文案、邮件、产品、语气和活动数据任务；模型卡明确不负责策略、市场研究和竞品分析 | 可作为未来英文文案对照，不替换孵化脑 |
| `aipgpt/Txt-Polisher` | 中文 Qwen2.5-14B SFT，约 1480 条来自少量抖音创作者的风格数据 | 只可在 `PresentationAdaptation` 做风格实验，存在模仿和风格坍缩风险 |
| 社区剪辑/运营 Agent 模型 | 多数训练工具轨迹、剪辑动作、标题或平台风格 | 适合“怎么做/怎么说”，不能证明“长期讲什么” |

公开微调模型的共同缺口是缺少内容根、候选路线、用户纠错、反例和长期结果标签。现在换模型或直接微调，
很可能只是把成稿写得更像平台内容，同时把错误内容世界说得更流利。第六版继续使用当前 GLM 做主链，等
`RootFeedbackRecord`、确认路线和真实运营结果形成跨行业留出集后，再比较 DSPy、排序器或领域微调。

最后一轮的路径为 `旧书 -> 扉页题字/藏书印如何揭示前藏主 -> 藏书印`，证明“确认路线 -> 精确地图 ->
命名召回 -> 网页取证 -> TopicBrief -> MessagePlan -> 基础稿 -> 表现形式”的主链能够真实跑通。它也暴露
出三次独立错误被事件流重复记录为 12 条；错误落在两类 Schema 漂移：`topic_brief` 被提供方包成 JSON
字符串，以及 `narrative_method_hint` 被写成字符串 `"null"`。这些不是内容根失败，却制造了重试和 Token
浪费。

## 本轮修复

1. 首次起号直接进入 `develop_account_strategy`，首份路线前不再擅自做泛网页搜索或竞品发现。
2. `SemanticReadingDraft` 仅解码明确的 JSON 数组字符串，普通文本仍按 Schema 拒绝。
3. 确认路线后的具体选题从台账重水化精确 `ComprehensionRecord`、候选地图版本及其哈希，不再拿“稿子、
   脚本、今天拍什么”重新做商业语义。
4. 用户当前真的引入新业务主体时，`subject_expression` 仍必须是当轮原话中的连续片段；历史别名只用于
   识别确认项目，不能覆盖新输入。
5. 不合法的可选 `topic_seed` 被丢弃并继续主链，不再让 Lead 的参数失误阻断整次请求。
6. 研究召回显式接收 `max_candidate_recall` 技术上限，模型可少给或不给，避免 24 条地图路径膨胀成
   22 个候选并撞上输出长度。
7. `TopicEditorialDecisionDraft` 只解包可解析为 JSON 对象的提供方字符串；普通文本仍失败。
8. `FormatDecisionDraft` 只将严格 JSON 字面量 `"null"` 归一为空值；其他字符串不会被静默吞掉。

## 采用边界

- **采用 Skills 的形态，不采用 Skill 包的世界观。** 每项 Skill 负责一个可评测任务，细节按需加载；
  内容根、账号路线和最终判断仍由现役领域合同与 Lead 负责。
- **采用改造型 Agent 的清晰交接，不采用自动营销流水线。** 对标、资料阅读和成稿可以由有界工作者完成，
  但不能靠关键词触发全套阶段，也不能让多个 Agent 投票决定内容根。
- **暂不替换或微调核心模型。** 当前失败更多来自上下文路由、工件续接、事实边界和输出 Schema；这些
  已通过真实运行定位。微调只在标签、反例和留出集成熟后进入离线竞赛。
- **不把一次合格选题等同于整套链路合格。** 旧书选题通过；66K Token、过长回答、未知素材和资源叙述
  仍是下一轮优化对象。

## 验证回执

- 变更聚焦回归：`167 passed` 。
- 指导文件预算门：修正文档超限后通过。
- 最终后端非 live 全量回归：`12247 passed, 76 skipped, 17 warnings in 517.62s`。
- 警告来自现有依赖的弃用提示和测试用短 HMAC 密钥，本轮无新失败。
- 实时模型主链已多轮运行；最后两项提供方兼容修复用精确回归验证，未再花费一次 60K+
  Token 重复相同业务样本。

## 下一步

1. 把最终回答压缩为“确认路线依据 + 一个今日选题 + 必要脚本”，大工件继续留在台账，不重复铺到聊天。
2. 将资源断言从自由叙述中再投影一次：未在 Brief 或证据中出现的能力和素材只能作为条件或未知。
3. 在全新业务上分别回归“首次起号、用户确认、确认后要一个选题”三种停止边界。
4. 从社区 Skills 中先挑选对标拆解、受众研究、开头与脚本流畅度四类做本地适配评测，不一次安装整包。
5. 只有新的跨行业用户纠错积累后，才启动 DSPy 或小排序器对照；现役运行时不在线自改提示词。
