# A111 账号业务意图与 TikTok LIVE 公会真实端到端审计

## 研究问题

用户说“我是做 TikTok 直播公会的，主要地区为 MENA 和 CCA，我该怎么起号”时，旧账号策略虽然会给
定位、人设、形式和变现，却没有先回答更基础的问题：公会在业务关系中是什么角色，账号需要影响谁，
对方为什么会在意，曝光之后希望对方采取什么行动，以及地区限定如何改变路线。结果是三条候选只把同一
定位分别包装成口播、无人素材和 AI 情景剧，并凭空新增 SaaS、课程、咨询或付费社群。

本轮验证的不是“公会行业模板”，而是一条跨行业成立的业务阅读边界：

```text
用户业务表达
-> 业务角色
-> 账号要完成的业务任务
-> 需要影响的人及其需求
-> 希望促成的行为
-> 地区与市场边界
-> 内容受众、账号定位、人设、表现形式和现有业务承接
```

曝光、播放和涨粉只是中间信号，不是最终业务目标。业务要影响的人也不必等同于愿意长期观看内容的人，
更不能等同于表现形式。

## 官方业务含义对照

TikTok 官方 LIVE Backstage 将 Creator Network 描述为支持 LIVE 创作者培养内容、发现机会并使用运营、
数据洞察和激励工具的组织。TikTok Newsroom 对合作 Agency 的说明也包含创作者数据管理、直播经验共享和
收益增长支持。这足以支持把“TikTok 直播公会”理解为连接平台和直播创作者、负责招募、培养与运营的
组织角色，而不是普通内容账号或泛营销公司。

TikTok Newsroom 在 2026 年的区域报道中将 CCA 展开为 Caucasus and Central Asia。运行时仍保留
用户原词 `MENA`、`CCA` 和具体覆盖范围未知，不把地区缩写自动扩展成未经项目确认的国家清单。

## 测试先行与实现

第一组失败测试要求每条新账号路线都显式给出：

- `business_role`
- `account_objective`
- `target_people`
- `target_need`
- `desired_action`
- `market_scope`

这些字段由模型在扁平 `AccountRouteOptionDraft` 中生成，再由代码编译为独立的
`AccountBusinessIntent`。已有台账中的该切面保持可空，避免破坏旧工件；新生成的路线必须填写。用户确认
路线时，该切面与定位、受众、人设、表现形式和变现一起进入确认版本。

第二组失败测试固定三条边界：

1. 候选路线不能只在表现形式上不同；内容主体、业务任务、目标对象、需求、动作和市场完全相同时拒绝。
2. 页面必须分别显示“需要影响的人”和“内容受众假设”，不能再合并成一个画像。
3. 业务身份本身不能自动进入人设可信资源；只有 Brief 明示的能力和资源才进入 `trust_basis`。

模型提示同时明确：账号变现只能服务用户已经声明的业务，不能为了填满方案新增课程、SaaS、咨询、付费
社群或其他生意。信息不足保留未知，不要求用户先绑定或登录平台账号。

## 真实运行对比

| 运行 | 调用 / Token | 结果 |
| --- | ---: | --- |
| 旧合同基线 | 7 / 26,118 | 三条路线主要按表现形式区分；地区弱化；新增泛化生意 |
| 新合同第一次 | 4 / 14,857 | 上游已识别公会角色和地区，但供应商修复返回 XML 工具调用，结构解析失败 |
| XML 精确兼容后 | 8 / 32,074 | 业务角色、招募对象、需求、入会动作和地区差异均进入三条策略路线 |

第一次新合同运行证明业务语义已经识别：`TikTok直播公会` 是招募和管理主播、对接平台资源的运营组织，
MENA 与 CCA 作为地区限定被保留。但旧结构兼容只扫描消息中的第一个 JSON 片段，无法读取供应商返回的
`<function_calls>` 包装。

修复只接受一个、名称与目标 Pydantic Schema 完全一致、总字节有上限、参数名不重复的 XML 调用；随后
仍由原 Schema 校验。多调用、错工具名、重复参数或格式不符的 `function_calls` XML 均不会放宽为成功。
这是供应商协议兼容，不是新的语义规则。

第二次端到端运行中，推荐路线已经明确：公会账号通过解释直播经纪与组织机制，让 MENA/CCA 潜在主播
理解公会模式、合作条件与自身利益，最终主动咨询入会。另两条路线分别选择公会经营透明度和跨区域生态
比较作为不同的长期位置；真人口播、图文或无人素材只作为各路线内部的表现手段。内容受众可以包含行业
观察者，但业务要影响的人仍是潜在合作主播，两者首次在输出中明确分开。

## 残留问题

- 输出仍把“用户做公会”推断成“掌握一手经验”“拥有实际案例”“天然具备跨区域视角”，而共同未知又
  承认这些资源未确认。`trust_basis` 已不再保存这些断言，但自由叙述中的事实边界尚未通过。
- 上游内容根收敛为较宽的“艺人经纪与组织管理”，并再次使用“博弈”措辞。它没有阻断业务理解，但是否
  适合该账号的长期内容位置仍只能记为部分通过。
- 第二次运行需要 8 次模型调用和 32,074 Token。新增业务切面不是主要成本；大头仍在上游语义家族、
  共同世界、内容根和地图生成。本轮不靠删除业务字段掩盖该成本。
- 运行没有正式对标和受众证据，因此路线只能是低到中置信度提案，不能宣称已经验证当地主播真实需求。

这些问题不能再用行业关键词硬门、资源黑名单或更多固定阶段修补。下一轮应在账号策略输出内部继续区分
“用户已陈述事实”和“路线成立条件”，并用新的跨行业案例验证，而不是重跑本例调提示词。

## 架构结论

`AccountBusinessIntent` 是账号路线的一个切面，不是新的强制工作流，也不进入内容地图。三层边界现在是：

```text
内容地图：这个主体有哪些可长期展开的内容世界
业务意图：账号要影响谁、解决什么需求、促成什么业务行为
表现形式：用真人、素材、数字人、情景剧或其他方式怎么呈现
```

定位要同时读取三者，但任何一层都不能代替另外两层。对用户只问单个选题的请求，系统仍可停在选题链；
只有“怎么起号、账号如何定位”才生成这份长期业务意图。

## 验收结论

TikTok LIVE 公会案例的主要业务理解已经通过：系统能够识别公会角色、潜在主播、主播决策需求、咨询或
入会动作，以及 MENA/CCA 对语言、文化和区域策略的影响；候选路线也不再只是三种拍法。

本轮总体状态为 `reviewed_with_live_e2e_and_residuals`，不能记为完全通过。资源与经验断言、上游内容根
精度和 Token 成本仍是显式未结项。
