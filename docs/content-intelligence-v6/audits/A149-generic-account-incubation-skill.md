# A149 通用起号 Skill 与根运行共享研究预算

## 问题

A148 证明极薄 Agent 内核可以显著降低成本，但裸模型没有把“我是做 TikTok 直播公会的，我该怎么起号”识别为
公开内容账号孵化，而是交付了公会经营 SOP。随后建立的通用 `account-incubation` Skill 能纠正任务所有权，却暴露
出第二个问题：正文里写“一次搜索、不要重试”并不能约束模型。两次真实公会运行分别在 66,461 和 83,473 Token
时因并行近义搜索、失败抓取和连续重试被人工中断。

这说明提示词可以告诉模型什么工作值得做，却不是可靠的执行预算。继续往正文添加“不得、必须、只许”会重新制造
第四版的硬门，而且仍不能处理并发工具调用。

## 方案

保留一个总 Agent 的判断权，只新增两层通用能力：

1. `account-incubation` 是延迟发现、显式激活的通用方法 Skill。它定义起号任务的目标，要求区分业务对象与内容
   受众，并交付方向和一个可直接拍摄的选题；它没有行业词表、固定阶段、固定样本数、日历或评分门。
2. Skill 可在 frontmatter 声明 `tool-call-budgets`。`SkillToolBudgetMiddleware` 只对本轮已激活 Skill 生效，在
   工具执行前原子预占额度；达到上限后，拒绝后续调用并从后续模型步移除相应 Tool Schema。提示只说明该工具不能
   重试，模型仍可自主判断是否使用其他工具、继续推理或交付当前结果。

预算限制的是费用、并发和重试，不判断受众、定位、内容根或选题是否正确。未激活 Skill、未列入预算的工具和下一次
新根 Run 均不受本轮额度影响。Slash 激活优先级、Agent 自主激活、用户隔离和现有 `allowed-tools` 权限边界保持不变。

首个公共 Skill 为能力发现、网页搜索、正文读取和抖音对标采集分别设置有界额度。一个共享组中的两个抖音对标工具
共用额度，防止模型通过换工具名绕过同类研究预算。调用在超时或报错前已经消耗额度，因此上游故障不会触发
无限重试；同步与异步并行调用共用同一把原子锁。

## 独立审计后的修正

首个实现把额度绑定到“当前 Skill”，独立审计发现四个真实缺陷：额度耗尽提示会命令模型“完成回答”；同一 Run 中
`A -> B -> A` 会刷新 A 的额度；父 Agent 与子 Agent 各有一份额度；工具执行时重新读取当前 Skill，使并行激活
可能改变已由上一模型步发出的工具调用所属预算。

修正版 `1.2.0` 将决策冻结在模型步：该步产生的工具调用始终使用当时的预算决策。每个根 Run 保存按 Skill 分开的
账本，切换回来继续使用原计数。原生子 Agent 只接收一个经过身份校验的随机 opaque carrier，计数器和锁仍留在
进程内，并与父 Agent 原子共享。carrier 绑定 `run_id + user_id + thread_id`，进入模型上下文、日志或前端前按
内部敏感上下文清理。跨进程或外部 Agent 不宣称共享；本合同只覆盖 DeerFlow 原生子 Agent。

## 测试驱动记录

实现前，新增测试首先因 `ToolCallBudget` 不存在而失败。独立审计后的失败测试又分别锁定 Skill 往返切换、模型步
冻结和父子共享。实现后，预算与 Task 传播聚焦回归为 `52 passed`，五个相邻 Skill 激活及真实 bootstrap 回归为
`5 passed`。正式后端非 live 全量回归为 `12679 passed, 76 skipped, 19 warnings in 511.17s`，退出码为 `0`；
不用真实运行结果替代代码回归。

## 真实运行

### 全新行业：工业安全培训

输入“我是做工业安全培训的，主要客户是化工园区，我该怎么起号”。运行成功结束，使用 5 次模型调用、22,266
Token、约 87.47 秒；轨迹只有 `describe_skill -> activate_skill -> tool_search -> web_search`。Agent 识别了起号
任务，给出内容受众、账号方向和具体题目，并在一次质量不佳的搜索后停止。

业务只部分通过：回答擅自写入“走进过无数化工园区的内部人”等用户经历和技术能力。搜索预算解决了失控，没有
自动解决事实归属。

### 目标回归：TikTok 直播公会

原样输入“我是做TikTok直播公会的，主要地区为MENA和CCA，我该怎么起号”。运行成功结束，使用 5 次模型调用、
23,516 Token、约 132.71 秒；工具轨迹同样收敛为 `describe_skill -> activate_skill -> tool_search -> web_search`。

相较 A148，本轮正确完成了三项关键工作：

- 明确当前任务是公会对外账号孵化，不是公会运营教程；
- 区分公会希望招募或合作的业务对象与内容真正需要吸引的人；
- 给出推荐方向和可直接拍摄的题目“直播公会到底靠谁赚钱：拆公会、代理、主播这条链，每一环拿走什么、留下
  什么坑”。

相较预算上线前两次被中断的运行，本轮分别少消耗至少 42,945 和 59,957 Token，并完成了最终回答。

业务仍不是完整通过：回答把用户使用中文推成中文内容账号的默认假设，写入若干未经正文核实的 MENA/CCA
市场判断，并推断用户拥有可讲述的亲历动作；本轮也没有取得真实抖音对标账号证据。回答已标注部分假设和证据
缺口，但这些内容仍不能作为项目事实。

## 结论

> 运行机制通过，通用起号判断部分通过，事实与用户能力绑定仍未通过。

本轮证明“不恢复固定孵化流水线”并不等于让裸模型独自工作。合适的分工是：薄身份内核负责目标与行动权，按需
Skill 提供当前方法，确定性中间件管理成本和并发，外部证据支持事实，Lead 完成最终判断。

后继不得针对直播公会、工业安全或某个错误句子继续给主提示词打补丁。下一边界应独立验证：最终回答中的第一人称
经历、能力和区域事实，能否逐项绑定用户原话、项目事实或已读来源；无法绑定的内容应降为明确假设或删除。同时应
提高真实平台对标采集的可用性，而不是把网页搜索摘要冒充对标。
