# 参考架构对照

## 共同结论

几套成熟资料使用不同术语，但核心收敛一致：

```text
模型不是整个 Agent
Agent = 模型判断 + 运行循环 + 有界上下文 + 工具/环境 + 状态 + 权限 + 反馈评测
```

它们也共同反对两个极端：一端是把所有步骤写死、模型只填表；另一端是把所有责任交给一段 Prompt、没有
状态与验证。

## 吴恩达：Agentic 设计模式

Andrew Ng 的课程把反思、工具使用、规划和多 Agent 作为可组合模式，重点是让系统迭代执行并用评测优化，
而不是一次生成答案。

对第六版最有价值的不是把四种模式做成四个强制节点，而是：

- 对开放任务允许模型计划和调整；
- 搜索、抖音、MediaKit、HLLM 等必须成为真实工具反馈；
- 草稿、选题、分析和制作都应能检查并修正；
- 用真实任务评测整个系统，而不是只评模型最后一句话。

## Harrison Chase / LangGraph：模型与外围代码分工

`AI Agents in LangGraph` 从手写 Agent Loop 开始，再引入 LangGraph 的状态、图、持久化和人工介入。最关键的
启发是：图是运行控制与恢复工具，不是业务思考本身。

第六版已有 LangGraph 底座，正确分工应是：

- 模型决定当前任务需要回答、搜索、调用 Skill、委派或执行；
- 图和中间件保证状态恢复、递归上限、权限、工具回填与异常语义；
- 只有发布、付款、删除、账号身份等确定性边界进入强制节点；
- “先画像、再拆词、再地图、再对标”不能因为能画成图就成为每轮必经路线。

## OpenAI：一个拥有用户关系的总控 Agent

OpenAI 将 Agent 定义为代表用户独立完成任务、由 LLM 管理执行并动态选择工具的系统。基础组件是模型、工具、
指令，运行核心是持续到退出条件的循环。

对第六版的直接映射：

- Lead 是唯一对用户交付和最终营销判断负责的总控；
- 先把单 Agent 加按需 Tool/Skill 做强，再为有证据的瓶颈增加子 Agent；
- 专家子 Agent 通过 Manager 模式返回有界结果，不直接修改业务台账或对用户作最终决定；
- Tool 定义要稳定、可复用、可测试，避免把 119 个接口全暴露给模型。

## Anthropic：Workflow 与 Agent 要分清

Anthropic 将预定代码路径称为 workflow，将模型动态决定过程和工具使用的系统称为 agent，并建议从简单、可组合
模式开始。其上下文工程进一步指出：每次推理的 Prompt、工具 Schema、MCP、外部数据和历史共同争夺有限注意力。

这解释了第六版此前“核心提示已经改薄，回答仍像顾问”的现象：模型看到的不只是核心提示，还看到全量 Skill
摘要、工具名、MCP 路由、工作区说明、引用规则和历史摘要。Agent 调优必须检查完整模型请求，不能只数一个
Python 常量的字符数。

## Claude Code：把不同能力放在不同扩展面

Claude Code 的公开设计可概括为：

```text
收集上下文 -> 行动 -> 验证 -> 重复
```

它将不同信息放在不同位置：

| 组件 | 作用 |
|---|---|
| `CLAUDE.md` | 用户/团队写的项目长期指令 |
| Skill | 按需加载的方法、知识和工作流 |
| MCP | 外部服务与工具 |
| Subagent | 独立上下文与权限的委派执行 |
| Hook | 必须确定执行的生命周期策略 |
| Auto memory | Agent 从历史中沉淀的可修正学习 |

这套分工直接支持第六版：业务事实不进 SOUL，行业方法不进项目指令，安全约束不只靠 Prompt，读 Skill 不等于
永久采用 Skill。

## Codex：没有 SOUL 文件，也有清晰身份层

Codex 证明“是否存在 `SOUL.md`”不是 Agent 判定标准。其基础 Prompt 已独立定义身份、协作方式、自主执行、
验证、用户沟通和工程判断；项目指令由有作用域的 `AGENTS.md` 提供；权限、环境、协作模式、插件和其他动态
上下文在代码里以有名字的类型管理。

Codex 最值得第六版采用的是上下文纪律：

- 上下文增量追加，避免频繁重写历史；
- 每类注入有名字、有所有者、有测试、有硬上限；
- 大块新模型上下文需要人工审查；
- 项目规则按作用域生效；
- 工具和环境变化能被检查，而非匿名拼接字符串。

因此第六版可以使用 `SOUL.md`，也可以使用 `IDENTITY.md` 或数据库对象；关键是它必须是独立、稳定、版本化、
可观察的身份层，而不是散落在业务 Prompt 与代码分支中。

## Hermes：文件职责分离最清楚

Hermes 的价值不是模型或某个提示词，而是把 Agent 长期上下文拆得直观：

| Hermes 文件 | 责任 | 第六版对应物 |
|---|---|---|
| `SOUL.md` | Agent 身份、人格、语气和价值取向 | 产品身份资产 |
| `USER.md` | 当前用户的稳定档案 | 用户级事实/偏好投影 |
| `MEMORY.md` | 环境、项目和工具学习 | 经审查的长期经验，不是业务真相 |
| `AGENTS.md` / `HERMES.md` | 项目级工作指令 | 仓库/项目规则与业务账本投影 |
| Skills | 按需程序和知识 | 第六版产品/行业 Skills |

Hermes 的 Prompt Assembly 采用稳定、上下文、易变分区。这个思想应采用，但不能机械复制：用户与项目数量多时，
数据库对象和内容寻址投影比每个账号手写 Markdown 更可靠。

## 最优组合，不换底座

第六版不需要再引入第二套运行时。合理组合是：

- DeerFlow/LangGraph：保留循环、恢复、工具、中间件、MCP、子 Agent 与 Gateway；
- OpenAI/Anthropic：定义 Agent、动态决策、单总控、上下文最小化与结果评测；
- Codex：采用类型化上下文、作用域、预算和可观测纪律；
- Claude Code：采用项目指令、Skill、MCP、Subagent、Hook 的责任分离；
- Hermes：采用 SOUL、USER、MEMORY、项目指令的直观分层；
- 第六版业务台账：继续作为用户、项目、账号、证据和结果的唯一业务真相源。

这不是把多个框架无限套起来，而是用它们共同证明的原则整理现有 DeerFlow。
