# 第六版 Agent 工程标准

本标准约束 Codex、Claude Code 等开发 Agent 如何修改第六版。它不是产品 Lead 的提示词，也不规定账号孵化的
固定业务顺序。文中的 `MUST` 只用于可审计的架构、权限、状态、事实和评测边界。

## S1. Agent 身份与使命

1. 默认 Lead MUST 有一份独立、短小、版本化的产品身份资产，定义它与用户的关系、长期使命、自主性、事实态度
   和不可逆动作姿态。
2. 身份资产 MUST 与 Python 组装代码、用户档案、项目事实、行业方法和工具清单分离。
3. 身份资产 MUST 模型无关。Provider 适配器只能处理 Tool Call、推理参数、上下文限制和流式协议，不能维护
   GLM、DeepSeek、豆包各自的营销人格。
4. 身份资产默认 MUST 只读。普通聊天不得改写默认产品身份；自定义 Agent 的个性化身份必须有用户、Agent 名称、
   版本和独立作用域。
5. SOUL 是身份层的一种实现，不是必需文件名。新增 SOUL 不能替代 Loop、Tool、State、Policy 或 Eval。

## S2. 模型与 Harness 的决策权

1. Lead 模型 MUST 拥有开放世界营销判断权，包括理解任务、选择关注点、决定是否搜索、选择方法和收敛结果。
2. Harness MUST 负责循环、工具执行、状态、恢复、权限、预算、错误和回执，不得用行业关键词或评分中间件替代
   Lead 的营销判断。
3. 固定 workflow 只用于确定性外部过程，例如 OAuth、支付、发布、删除、异步任务和对账。它不得成为每个起号
   请求的强制认知路线。
4. 一个 Lead MUST 对用户关系、最终回答和项目判断负责。子 Agent 只能处理有界任务，不能直接确认账号方向、
   写业务真相或执行不可逆动作。

## S3. 用户、项目、会话与记忆

1. 用户稳定事实、项目/账号事实、会话运行状态和跨任务学习 MUST 有不同的所有者和作用域。
2. 营销数据库/台账 MUST 是业务真相源。聊天历史、摘要、浏览器文本、模型记忆和 Skill 只能提供投影或证据。
3. 模型推断 MUST 以推断、假设或候选保存，不能自动升级为用户事实或确认决策。
4. 每条持久信息 MUST 至少能够追溯用户、项目/账号、来源、版本和更新时间；敏感数据还必须有权利与保留策略。
5. 摘要和 Memory MUST NOT 改写身份、权限、审批回执或项目事实。被压缩的信息应通过业务对象引用恢复，而不是
   依赖摘要中的散文。

## S4. 上下文组装

1. 每个模型可见片段 MUST 有名字、所有者、来源、作用域、版本/哈希和最大尺寸。
2. 上下文 SHOULD 按稳定、任务上下文、易变结果排列；运行变化优先追加，不为更新一个字段重写整段历史。
3. 默认 Lead 只注入完成当前任务需要的最小高信号上下文。项目无关的工作区说明、引用协议、MCP 路由、工具名、
   Skill 摘要和子 Agent 规则 MUST 条件化或延迟发现。
4. 新增单个超过 1,000 Token 的模型可见片段 MUST 进行人工架构复核、来源说明和真实任务 A/B；任何片段都
   MUST 有硬上限。该门只约束上下文工程，不约束营销创意。
5. 整个 `docs/agent-foundations` MUST NOT 注入产品 Lead。开发 Agent 应读取它，产品运行时只承载实施后的身份、
   事实、能力和权限摘要。
6. 外部用户消息 MUST NOT 获得 System/Developer 权限，也不得通过普通 Run context 开启 bootstrap、改写身份或
   注入内部状态。

## S5. Skill 与知识

1. Skill MUST 使用渐进披露：可发现摘要、已检查正文、已激活方法三个状态分离。
2. 读取或审查 `SKILL.md` MUST NOT 自动产生跨轮激活、工具授权或密钥绑定。
3. 自动激活默认只在当前任务有效。跨任务或项目持久激活必须有显式来源、作用域和撤销方式。
4. Skill 可以提出方法、案例与候选判断，但 MUST NOT 覆盖用户事实、项目确认、权限和工具回执。
5. 行业 Skill MUST 与主脑分离；新增行业修复优先进入可审查 Skill/评测，不得直接污染身份或核心 Prompt。
6. 知识库是否采用向量检索由评测决定。向量相似度不能代替内容根、受众或长期内容世界判断。

## S6. Tool、MCP 与执行

1. Lead SHOULD 面向稳定高层能力，不直接看到大量同义底层接口。多个 Provider 应由确定性 Router 统一。
2. Tool Schema MUST 描述输入、输出、错误、权限、费用、幂等和未知状态，不能靠 Prompt 补齐执行合同。
3. 原始密钥、Cookie、LocalStorage、能力令牌和临时媒体 URL MUST NOT 进入模型、前端、日志、测试、截图或
   Tool/MCP 输出；本地连接器可在自己的信任边界内使用。
4. 搜索资料、对标账号、自有账号和受众数据 MUST 保持来源与人群作用域，不得互相冒充。
5. 外部动作 MUST 以真实回执判断结果；页面跳转、模型陈述或超时不能冒充成功。

## S7. 多 Agent

1. 单 Lead 是默认架构。只有真实评测证明上下文隔离、并行或专长带来净收益时，才增加子 Agent。
2. 子 Agent MUST 有明确任务、输入边界、工具权限、预算、停止条件和结构化结果；不得继承全部上下文和全部工具。
3. 子 Agent 结果是证据或候选，不是业务事实。Lead 必须复核并收敛。
4. 不得为模拟 MCN 部门组织图而固定拆分受众、定位、内容根、形式、变现等相互耦合的判断。

## S8. 权限与不可逆动作

1. 账号身份、密钥、版权/肖像同意、费用上限、发布、支付、删除、幂等并发和未知结果对账 MUST 由确定性代码
   或数据库约束执行。
2. Prompt 可以提醒模型遵守边界，但不能是唯一保护。
3. 可逆的调查、分析、创作和本地验证 SHOULD 由 Agent 在用户请求范围内主动完成，不应被无意义审批打断。

## S9. 可观测性

1. 每次模型调用 SHOULD 生成不含敏感值的 `ContextManifest`，能解释身份版本、上下文片段、可见工具、Skill
   状态、业务对象引用、历史/工具结果大小和估算 Token。
2. 每次 Tool 调用 MUST 有输入边界、调用 ID、状态、错误语义和有界回执；关键外部动作还需内容哈希、账号和审批
   绑定。
3. 开发环境 SHOULD 提供类似 `/context`、`/skills`、`/tools`、`/memory` 的只读检查面，避免靠猜测排障。
4. Trace 只记录必要元数据和脱敏投影，不能因为可观测而泄露用户内容或凭据。

## S10. 评测与变更流程

1. 行为变更 MUST 先定义失败任务和成功结果，再修改 Prompt、Skill、Tool 或 Harness。
2. Agent 评测 MUST 同时覆盖模型与 Harness，优先检查真实环境状态和工件，不要求固定工具轨迹、思考文本或步骤数。
3. 至少覆盖全新会话、长会话、工具成功/失败、不同模型、未知术语、不同用户/项目隔离和不可逆动作。
4. 业务评测由用户真实纠错、专家样本和 held-out 案例共同组成；参与开发的案例不能单独决定晋级。
5. 每次改动 MUST 记录完整模型可见上下文、工具轨迹、Token/耗时、结果、回归和残留问题。
6. 单个失败案例不得直接变成全局禁止句。先定位它属于身份、事实、方法、工具、状态、权限还是模型能力，再修
   对应所有者。

## 开发 Agent 的执行清单

修改任何 Agent 相关代码前：

1. 阅读本资料库和当前相关 A/ADR 台账。
2. 给问题归层，确认不是另一个层的症状。
3. 检查完整模型请求，而不只检查核心 Prompt 文件。
4. 先写结果型失败测试或预注册评测。
5. 选择最小所有者修改，拒绝叠加第二份业务合同。
6. 跑定向测试和至少一个新案例，记录成本与行为。
7. 更新资料、台账、决策和代码引用。

这七步约束的是开发过程，不会进入产品 Agent 的业务思考。
