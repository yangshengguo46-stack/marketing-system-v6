# 上下文与文件模型

## 为什么要分层

模型不会只听“核心提示词”。一次真实推理可能同时包含身份、用户输入、项目事实、历史摘要、Skill、工具 Schema、
MCP 路由、权限、当前时间和工具结果。它们都在争夺注意力，也都可能改变行为。

因此，Prompt 工程的上位概念是 Context Engineering：决定什么信息在什么时机、以什么权限、进入哪次推理。

## 第六版八层上下文

| 层 | 名称 | 内容 | 典型存储 | 注入时机 |
|---:|---|---|---|---|
| L0 | 系统权限 | 身份隔离、凭据、审批、费用、幂等、不可逆动作 | 代码、配置、数据库约束 | 执行时确定性生效；只给模型必要摘要 |
| L1 | 产品身份 | Agent 是谁、替谁工作、长期使命、协作姿态 | 版本化身份资产 | 每个 Lead 会话稳定注入 |
| L2 | 用户档案 | 用户稳定事实、偏好、稳定限制 | 用户级结构化存储 | 与任务相关时有界投影 |
| L3 | 项目/账号事实 | 业务、受众假设、确认方向、内容资产、证据和结果 | 业务台账 | 按当前项目和任务投影 |
| L4 | 会话状态 | 当前请求、最近决定、工具结果、待处理状态 | LangGraph state/checkpoint | 当前轮动态注入 |
| L5 | 方法与知识 | 通用方法、行业经验、案例、参考资料 | Skill/知识库 | 先发现，真正需要时加载 |
| L6 | 工具与环境 | Tool Schema、MCP、文件、浏览器、MediaKit | Tool registry / MCP | 只暴露当前可能需要的能力 |
| L7 | 评测与学习 | 运行轨迹、结果评分、复盘、候选经验 | 评测集、回执、LearningClaim | 离线评测或下一任务的有界投影 |

L0 不等于“更多禁止句”；它主要由代码执行。L1 不等于项目知识。L2/L3 不能被聊天摘要或模型推断冒充。
L5 的方法不能修改 L0 权限，也不能自动改写 L3 事实。

## 建议的产品文件与对象

文件名不是硬要求，职责是硬要求。第六版建议采用：

```text
backend/packages/harness/deerflow/agents/lead_agent/
  IDENTITY.md                 # L1：默认产品 Agent 身份，短、稳定、版本化

业务存储
  UserProfile                # L2：用户事实与偏好
  IPProject / Account        # L3：项目与账号作用域
  Evidence / Direction ...   # L3：版本化业务真相

LangGraph
  ThreadState / checkpoint   # L4：当前运行状态

skills/
  */SKILL.md                 # L5：按需方法与行业知识

Tool/MCP registry            # L6：能力、Schema、权限与执行
Eval/receipts                # L7：真实结果与学习证据
```

`IDENTITY.md` 可以对产品展示为“SOUL”，但不直接允许普通对话自我改写。身份升级走 Git、评测和发布；用户对某个
自定义 Agent 的个性化修改则进入独立、自有作用域。

## 产品身份的合格合同

身份层应满足：

- 独立文件或结构化对象，不能只散落在 Python 拼接字符串中；
- 有版本和内容哈希，可知道某次运行用了哪一版；
- 默认只读，修改经过明确管理面或代码评审；
- 只包含长期稳定语义；
- 模型无关，不为 GLM、DeepSeek、豆包分别维护业务人格；
- 首轮完整注入有字节/Token 预算；
- 能在上下文检查器中显示来源，不暴露隐藏系统权限文本。

## 用户与项目必须分开

`USER` 记录跨项目稳定信息，例如用户希望 Agent 像员工一样主动、用户不懂代码、偏好中文沟通。项目台账记录
某个品牌、产品或账号的事实与决定。两者混在一起会造成：

- 一个项目的受众假设污染另一个项目；
- Agent 把一次临时创意当成用户永久偏好；
- 用户更换账号后仍被旧方向牵引；
- 无法明确删除、纠正或追溯一条信息。

任何自动学习先保存为候选，标记来源、作用域、置信和更新时间；不能因为模型重复说了几次就升级为事实。

现役 `UserProfile` 采用更窄的首版合同：只接受最后一条可见用户消息中的精确原文，支持显式记住、纠正和删除，
最多 16 条并按用户保存不可变修订。Lead 每次调用获得最多 2,400 字节投影，当前用户消息优先；子 Agent 不获得
修改能力。项目事实、模型推断和操作授权一律留在画像之外。首版不需要向量检索或自动抽取。

## Skill 的三种状态

现役最大结构问题之一是把“读过”近似成“激活”。正确状态至少是：

1. **可发现**：名称和短用途摘要进入索引，正文未加载。
2. **已检查**：Agent 为判断是否适用读取了正文；只对当前判断提供证据，不改变未来权限。
3. **已激活**：用户显式调用，或 Agent 明确选择在当前任务采用；可在有界作用域内影响方法与允许工具。

激活还必须带作用域：`turn`、`task` 或显式持久项目绑定。默认是当前任务，不能因为历史上读过一次就永久活跃。
Skill 退役、禁用或内容更新后，旧激活不得继续绑定凭据或工具。

## Tool 与 Skill 的边界

- Skill 说“怎么做得更好”；Tool 负责“真实做一件事”。
- Tool 返回结构化事实、错误和回执，不向模型暗示行业结论。
- 多个底层 Provider 应通过一个高层能力路由，例如 `BenchmarkCapability`，而不是把一排相似 Tool 全塞给 Lead。
- 原始 Cookie、Token、密钥和浏览器存储可以由本地连接器使用，但不得进入模型上下文、前端、日志或工具输出。
- 工具是否可执行由权限层决定，不由 Skill 文本自我授权。

## 稳定、上下文、易变的组装顺序

参考 Hermes 与 Codex，模型上下文应按以下顺序组装，并对每项记录来源和预算：

```text
稳定：权限摘要、产品身份、模型/运行能力基本合同
上下文：当前用户、项目、账号、显式激活 Skill、相关工具
易变：当前请求、时间、近期状态、工具结果、当前轮临时证据
```

旧消息不应为更新一个动态字段而整体重写；摘要不能改写产品身份、用户事实和业务台账。每次压缩后应能指出
哪些信息是摘要、哪些是原始事实引用。

## Context Manifest

每次模型调用应能生成不含密钥和大段隐私的只读清单：

```text
model / provider
identity_version / identity_hash / bytes
context_fragments[name, owner, scope, source, hash, bytes]
visible_tools[name, schema_hash, bytes]
skills[discoverable, inspected, activated, scope, version]
project_artifact_refs
history_bytes / tool_result_bytes / estimated_tokens
```

Manifest 首先用于开发审计和评测，不必把完整系统提示暴露给最终用户。它必须能回答：“为什么一句你好消耗这么多
Token”“这次为什么调用抖音而不是网页”“哪个 Skill 改变了后续工具权限”。
