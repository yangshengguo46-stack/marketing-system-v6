# 第六版 Agent 符合性审计

审计日期：2026-08-23。对象为 `codex/v6-comprehension-core` 当前工作树。工作树包含尚未提交的 A140-A143 与
安全/上下文修复，因此“已修复”不等于已发布。

## 总判断

第六版**是正经 Agent runtime**：模型能够在 LangGraph 循环里动态回答、调用 Tool/MCP、读取 Skill、委派
子 Agent、接收环境结果、恢复状态并继续工作。它不是把起号步骤写死后让模型填表。

但它还不是产品化完成的“新媒体运营员工 Agent”。目前更准确的状态是：

> 一套能力很强的通用 Agent Harness，已经完成薄员工内核、版本化身份、显式 Skill 生命周期、调用清单和最小
> UserProfile；项目上下文检查面、长期学习和产品级装配还没有全部收口。

## 已经做对的部分

### 保留

- DeerFlow/LangGraph 作为唯一运行时；不再嵌入 Codex、Hermes、Dify 或其他第二 Agent runtime。
- 一个 Lead 拥有用户关系和最终营销判断；子 Agent 只按需委派。
- 极薄、模型无关的员工内核，继续排除行业答案、固定起号步骤和平台规则。
- 项目、账号、证据、方向、内容工件和结果使用结构化台账与版本父级。
- Skill、Tool、MCP 的渐进发现方向。
- 浏览器、抖音、MediaKit、HLLM 作为证据/执行能力，不拥有营销判断权。
- 权限、审批、幂等、费用、身份和不可逆动作由代码负责。
- A/ADR/evidence 台账与测试驱动的工作方式。

## 应退役或隔离的部分

- A137 之前遗留的多份生产业务母合同，只保留在实验/历史审计，不再参与现役 Prompt。
- 通用 MCP 服务器级关键词强路由。A143 工作树已关闭，后续只允许精确能力元数据或自然工具搜索。
- 静态暴露全部延迟 Tool 名称。工具留在目录中，但首轮不应看到内部应用流程清单。
- 任意历史 Skill 读取形成的永久“Active skills”。迁移后旧记录只能作为“曾检查”证据，不能继续授权。
- 把会话摘要、Memory、SOUL 或 Skill 当成项目业务真相的任何实现。

5. 已建立最小 UserProfile 投影与纠正机制，并完成真实 GLM 新会话验收；下一步只做前端管理与跨模型验证。

每一步单独评测和提交，禁止再同时重写身份、方法、工具和业务对象。

## 验收问题

完成后，系统必须能明确回答：

- 这次 Agent 用的是哪版身份？
- 它知道的哪些是用户事实、哪些是项目事实、哪些只是模型推断？
- 哪个 Skill 只是看过，哪个在当前任务真正生效？
- 它为什么看到这些工具，为什么有权执行？
- 它对环境做了什么，结果由什么回执证明？
- 一句简单问候为什么消耗这些 Token？
- 新行业表现变好，是模型、上下文、Skill、工具还是数据造成的？

身份版本、Skill 激活来源、用户画像版本和单次 Token 开销现在都能从 ContextManifest 回答。项目事实的统一检查、
工具权限的完整来源说明和统一产品检查面仍未收口，因此产品 Agent 化还不能宣告完成。
